      core-banking-ledger
      
          
      A core banking backend where every rupee movement is a balanced journal in an append-only ledger, corrected only by reversal, and published to Kafka through a transactional outbox so downstream systems see every posting exactly once and in order.
      
          
        
            
      • Lock ordering instead of SERIALIZABLE. A transfer locks both balance rows in ascending account-id order under READ COMMITTED with a lock timeout. Opposite transfers queue instead of deadlocking, and nothing waits forever.
        • 
            
      • Idempotency decided by the database. The key is claimed by a unique insert in its own short transaction, so two concurrent retries are settled by a constraint, not by application code.
        • 
            
      • Maker-checker with holds. Above a threshold the raiser cannot post. Available balance drops, ledger balance does not, and a different CHECKER role decides. Undecided transfers expire by a ShedLock-guarded sweep.
        • 
            
      • Append-only enforced in Postgres. Triggers reject UPDATE, DELETE and TRUNCATE on journal, ledger and audit tables. A nightly job recomputes every balance from the lines and reports any drift as a metric and an audit row.
        • 
          
      
          
      Also: keyset pagination for statements, daily interest accrual with HALF_EVEN month-end payout, RFC 9457 problem responses, OpenAPI 3.1, Prometheus metrics, ECS JSON logs, Testcontainers, ArchUnit, multi-stage Docker, GitHub Actions.

      ecommerce-backend
      
          
      A shop API built around the parts that break under real traffic: stock that cannot be oversold, orders that can be retried safely, refresh tokens that rotate, and emails that only go out after the database commits.
      
          
        
            
      • One conditional UPDATE per line. stock = stock − ? WHERE stock ≥ ?, lines reserved in product-id order. A test fires 20 concurrent buyers at the last 5 units and expects exactly 5 orders. That test is Lab 1 above.
        • 
            
      • Idempotent order placement. Key, user, SHA-256 of the body and the response are stored in the order transaction. Replay returns the stored response; same key with a different body is 422. That is Lab 2.
        • 
            
      • Refresh-token families. 256-bit opaque tokens stored as hashes, rotated on every use. Replaying a used token revokes the whole family.
        • 
            
      • Side effects after commit. Notifications run on @TransactionalEventListener(AFTER_COMMIT) with the correlation id copied to the worker thread. A rolled-back order never sends an email.
        • 
          
      
          
      Also: order state machine with audit history, Strategy-pattern payment processors recorded with REQUIRES_NEW, Redis cache evicted after commit, Bucket4j login limits, statement-count tests against N+1.

      GeoGuard
      
          
      A group creates a safe zone. When any member leaves it, everyone else gets a push, even with the app killed. Built as a take-home assignment for an Android role, with a signed APK in the releases you can install on two phones and try.
      
          
        
            
      • OS geofencing instead of polling GPS. Battery-safe and works in the background with no foreground notification. Trade-off accepted: 1–2 minute latency and a 150 m minimum radius.
        • 
            
      • Exit events survive bad networks. BroadcastReceiver → WorkManager → Firestore, with retries. Deterministic event ids (uid_EXIT_time) mean a retry can never create a duplicate alert.
        • 
            
      • Fan-out on the server. A Cloud Function sends FCM to every other member, so no secrets ship in the APK and receivers get alerts with the app closed.
        • 
            
      • Jitter cooldown and reboot resync. One alert per member per group per 5 minutes; geofences are re-registered after reboot.
        • 
          
      
          
      Security rules: only members read a group, users can only add themselves and only report their own exits, push tokens are private, groups cannot be listed.

      About
      
    
      
      
      Why the ledger paper.
      
      
      
        
      
          
      Bookkeepers solved "how do we trust a number nobody can un-write?" centuries before databases existed: write every movement twice, never erase, correct with a new entry. Most of what I care about in backend engineering is that same instinct applied to concurrent systems, so this page is set on a ledger.
      
          
      I'm Darshan Sonawane, a backend and Android engineer. The pattern across my repositories is the same: pick the one guarantee that matters (no oversold unit, no double charge, no unbalanced journal, no missed exit event), write the test that would catch its failure, then build until that test is green and keep it green in CI.
      
          
      I learn by building the hard version of the thing: the ledger instead of a to-do app, the race test instead of a screenshot, the state machine with all 49 transitions tested instead of a happy path. What I can show is systems that hold up when you push on them, and the tests that prove it.
